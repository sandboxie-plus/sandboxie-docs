# プロセス グループ

`ProcessGroup` は、実行可能イメージ セレクターの再利用可能な名前付きセットを定義します。プロセス修飾セレクターを受け入れる設定は、対応するランタイム パーサーがプロセス グループをサポートする場合、各実行可能ファイル名を繰り返す代わりにグループを参照できます。

例:

```ini
[DefaultBox]
ProcessGroup=<Browsers>,firefox.exe,chrome.exe
```

この定義だけでは、アクセスを付与または拒否したり、プログラムをサンドボックスに強制したり、プロセスを開始または停止したり、Windows プロセス グループまたは Job Object を作成したり、その他の方法でポリシーを適用したりしません。グループがランタイム動作に影響を与える前に、2 つ目の設定が `<Browsers>` をそのプロセス セレクターとして使用する必要があります。

Sandboxie のドライバー側と SbieDll ユーザー モードの両方の構成マッチャーは、それらのマッチャーを使用する設定のためにプロセス グループを解決します。これは、すべての Sandboxie 設定がプロセス グループを受け入れることを意味するものではありません。それを参照する設定の構文を確認してください。

## 構文

一般的な形式は次のとおりです。

```ini
ProcessGroup=<GroupName>,program1.exe,program2.exe
```

山かっこはグループ セレクターの一部です。現在のランタイム マッチングは、セレクターが `<` で始まるときにグループ参照を認識します。`Browsers` のような裸の名前は、`<Browsers>` という名前の `ProcessGroup` としてではなく、通常のイメージ セレクターとして扱われます。

グループ名と通常の実行可能イメージ メンバーシップの一致は大文字と小文字を区別しません。プロセス ID や完全な実行可能ファイル パスではなく、`firefox.exe` のような実行可能イメージ名を使用してください。

一部の汎用構成マッチャーはワイルドカード イメージ パターンを解釈できますが、すべてのアクティブなプロセス グループ マッチング パスがそうするわけではありません。コンシューマー間で一貫して動作する必要がある構成には、ワイルドカード メンバーではなくリテラルの実行可能イメージ名とネストされたグループ参照を使用してください。

否定は、`ProcessGroup` 定義ではなく、グループを使用するルール内のプロセス セレクターに属します。設定が否定プロセス セレクターをサポートする場合:

- `<Browsers>` はグループのメンバーに一致します。
- `!<Browsers>` はグループのメンバーでないプロセスに一致します。

グループを `ProcessGroup=!<Browsers>,...` として定義しないでください。

## ルールでのグループの使用

このリソース アクセスの例は、ファイル ルールを `<Browsers>` のメンバーに適用します。

```ini
[DefaultBox]
ProcessGroup=<Browsers>,firefox.exe,chrome.exe
OpenFilePath=<Browsers>,C:\Shared\*
```

`OpenFilePath` は実証済みのコンシューマーの 1 つですが、唯一ではありません。組み込みテンプレートも、ファイル、レジストリ、IPC、およびウィンドウ クラス ルールでプロセス グループを使用します。

Sandboxie の汎用プロセス一致レベルを使用するコンシューマーでは、直接の実行可能ファイルまたはグループの一致が、否定セレクターより強いプロセス一致優先度を持ち、否定セレクターはグローバルまたは `*` セレクターより強くなります。これは修飾ルール間の優先順位です。`ProcessGroup` 内のメンバーの順序は、あるメンバーが別のメンバーより優先されるようにしません。

## ネストされたグループ

プロセス グループは別のプロセス グループを含むことができます。

```ini
[DefaultBox]
ProcessGroup=<Browsers>,firefox.exe,chrome.exe
ProcessGroup=<WebApps>,<Browsers>,electron-app.exe
```

したがって `<WebApps>` は `firefox.exe`、`chrome.exe`、および `electron-app.exe` に一致できます。

ネストされた展開は、現在のランタイムで意図的に深さが制限されています。循環的または過度に深い定義による展開は、無限に再帰するのではなく制限されますが、そのような定義は有用な構成ではなく、依存すべきではありません。SandMan は既存のグループをメンバーとして選択できますが、現在、直接または間接的な循環を防いでいません。

## 繰り返しおよび継承された定義

同じグループ名を持つ繰り返し定義は、追加のメンバーを提供します。

```ini
ProcessGroup=<Browsers>,firefox.exe
ProcessGroup=<Browsers>,chrome.exe
```

有効なグループはどちらの実行可能ファイルにも一致します。同じ名前の定義がボックス、`[GlobalSettings]`、または有効なテンプレートから来る場合も同じランタイム動作が適用されます。該当する定義は、ソースによって 1 つの定義が選択されるのではなく、メンバーを提供します。したがって:

- `[GlobalSettings]` は通常のグローバル構成ルックアップを通じてサンドボックスにグループを提供できます。
- 有効なテンプレートはグループを提供できます。
- 同じ名前のボックス ローカル定義は、ランタイムで継承されたメンバーを削除しません。
- 複数の有効なテンプレートからの同じ名前の定義もメンバーを提供します。

現在の SandMan の説明では、ボックスに定義されたグループがテンプレートに定義されたグループを上書きすると述べています。その文言は、該当するすべての同じ名前の定義を検査する現在のランタイム マッチャーを反映していません。偶発的な結合メンバーシップが不明確になる場合は、構成ソースをまたいでグループ名を再利用しないでください。

## SandMan でのグループの管理

**Sandbox Options > Program Groups** を開きます。ページは次を提供します。

- **Add Group**
- **Add Program**
- **Remove**
- **Show Templates**

**Add Group** は入力された名前を山かっこで保存します。**Add Program** は既存のグループを選択でき、**Group: GroupName** として表示され、ネストされたグループ参照を作成します。

**Show Templates** は `[GlobalSettings]` とボックスの有効なテンプレートからのグループをローカル グループと並べて表示します。テンプレート由来のエントリはこのビューでは読み取り専用です。ページはボックスのローカル `ProcessGroup` エントリのみを書き込みます。

このページでローカル グループの名前を変更すると、その定義名が変わりますが、グローバルなリファクタリング操作ではありません。他のプロセス グループまたは構成ルール内の古い名前への参照は自動的に書き換えられません。グループを削除すると同様に、それを参照する設定を必ずしも削除することなく、選択された定義が削除されます。削除された定義を通じて未解決のグループ セレクターは一致できませんが、同じ名前の別の該当する定義が依然としてメンバーを提供する場合があります。

## UI 管理のグループ

一部の高レベルの SandMan 機能は `ProcessGroup` エントリを内部的に維持します。現在の例には、Internet Access および Start/Run 制限で使用されるプログラム リストがあり、`<InternetAccess>`、`<StartRunAccess>`、`<StartRunAccessDisabled>` などのグループがあります。

したがって、これらのエントリを手動で編集または削除すると、それらのコントロールが表す内容が変わる可能性があります。これらの名前は通常のランタイム プロセス グループであり、その重要性はそれらを参照するルールと SandMan 機能から来ます。

## ProcessGroup と BoxGrouping

`ProcessGroup` と [`BoxGrouping`](BoxGrouping.md) は無関係な目的を果たします。

| 設定 | 含むもの | スコープと効果 |
| ------- | -------- | ---------------- |
| `ProcessGroup` | 実行可能イメージ セレクターとネストされたプロセス グループ | ランタイム ルール マッチングで使用されるサンドボックス、グローバル、またはテンプレート構成。`<GroupName>` として参照されます |
| `BoxGrouping` | サンドボックスと視覚的なサブグループ | ユーザーごとの SandMan 階層と順序付けメタデータ。ランタイム ポリシー効果なし |

2 つのサンドボックスを同じ `BoxGrouping` ブランチに置いても、それらの `ProcessGroup` 定義が共有されたり、それらのサンドボックス内のプロセスが共通のプロセス グループのメンバーになったりしません。

## 変更の適用

`ProcessGroup` の変更を保存すると構成が更新されますが、新しいメンバーシップがいつ観察可能になるかは、グループを参照する設定に依存します。動的に評価されるチェックは後続の操作で更新された定義を使用できますが、プロセスの初期化中に有効なルールを構築またはキャッシュするコンシューマーは、影響を受けるサンドボックス化されたプロセスの再起動を必要とする場合があります。SandMan、サービス、またはドライバーの再起動は、通常、プロセス グループを変更するためだけには必要ありません。

## Sandboxie Plus と Classic

`ProcessGroup` は共有ランタイム構成メカニズムであり、Sandboxie Plus 専用機能ではありません。SandMan は現在の **Program Groups** ページを提供し、Sandboxie Control Classic もプログラム グループの構成と選択のサポートを含んでいます。それらのインターフェイスは同一ではありませんが、互換性のある INI 定義は共有ランタイムによって消費されます。

## バージョン履歴

現在の設定メタデータは `ProcessGroup` の `AddedVersion` を記録していないため、ここでは正確な導入バージョンは確立されていません。プログラム グループの処理は Sandboxie Plus 0.4.3 / Classic 5.43.7 より前から存在します。そのリリースは、ランタイム設定を導入するのではなく、SandMan UI の解析を修正しました。以降の SandMan リリースでも追加のプログラム グループ UI の問題が修正されました。
