# プロセス速度設定

プロセス速度設定は [Sandboxie Ini](SandboxieIni.md) のサンドボックス設定で、Sandboxie Plus 1.14.0 以降で利用できます。サンドボックス化されたプロセス内の選択された Windows タイミング、スリープ、およびタイマー API を調整します。Windows のシステム クロックを変更したり、サンドボックスのための完全な時間仮想化を提供したりしません。

## プロセス速度変更の有効化 {#enabling-process-speed-changes}

サンドボックスのためにこの機能を有効にするには:

```ini
[DefaultBox]
UseChangeSpeed=y
```

`UseChangeSpeed=y` は、該当するタイミング フックをそれらの初期化中にインストールできるようにします。そのランタイム フォールバックは無効 (`n`) です。値はサンドボックス セクション、該当する有効なテンプレート、または `[GlobalSettings]` から取得できます。直接のサンドボックス セクションに存在しないことは、必ずしも機能を無効にするわけではありません。有効な値がそれを有効にしない場合、対応するフックはインストールされません。

小さな正の 10 進整数係数を使用してください。6 つの係数はすべてコンシューマー フォールバックが `1`、つまり通常の中立値です。通常のリテラル `0` 値もそのフォールバックに解決されます。`AddSleepSpeed=0` はスリープ呼び出しをスキップする指示ではなく、ゼロを機能の無効化に使用すべきではありません。

## 影響を受ける API

設定は以下にリストされた API グループにのみ適用されます。

### ティックおよびクロック関数 {#tick-and-clock-functions}

`AddTickSpeed` と `LowTickSpeed` は次を制御します。

- `GetTickCount`
- `GetTickCount64`
- `QueryUnbiasedInterruptTime`
- `QueryPerformanceCounter`

演算限界内の小さな正の値の場合、リストされたクロックのほとんどはおおよそ `AddTickSpeed / LowTickSpeed` でスケールしますが、それらの計算は異なります。`GetTickCount` は、そのフックがインストールされたときに取得されたネイティブ参照に対して経過値をスケールします。`GetTickCount64` と `QueryPerformanceCounter` は絶対ネイティブ値をスケールします。この機能は対応する `QueryPerformanceFrequency` フックをインストールしません。

現在の実装では、`QueryUnbiasedInterruptTime` はその結果をスケールする前に整数係数を除算します。他のリストされたクロックとは異なり、1 未満の分数比は、比例して遅いクロックではなくゼロを生成する可能性があります。`3/2` のような比率は `1` に切り捨てられます。これは現在の実装上の制限であり、一貫した分数スケーリングの契約ではありません。[現在のクロック ラッパー](https://github.com/sandboxie-plus/Sandboxie/blob/31ba1e5c1aaaf3c98248a8994aecc9d016b7a310/Sandboxie/core/dll/kernel.c#L326-L401)を参照してください。

これらの関数は経過時間またはパフォーマンス カウンター時間を表し、システムの日付と時刻ではありません。影響を受けるタイミング ソースは独立して調整され、単一の正確な仮想クロックとして扱うべきではありません。異なる Windows タイミング ソースを比較するアプリケーションは違いを観察する場合があります。

### スリープ関数 {#sleep-functions}

`AddSleepSpeed` と `LowSleepSpeed` は、Sandboxie の `SleepEx` フックを通じて渡される要求された期間を制御します。Sandboxie は別個の `Sleep` フックをインストールしません。通常の `Sleep` 呼び出しは、その実際の Windows 実行パスが傍受された `SleepEx` 実装に到達する場合にのみ影響を受けます。

演算限界内の通常の正の値の場合、転送される期間はおおよそ `要求された期間 * LowSleepSpeed / AddSleepSpeed` です。より短い要求された遅延は、実行をより速く進められるようにします。もう一方の係数を `1` のままにすると:

- `AddSleepSpeed=2` は要求された 1000 ms のスリープを 500 ms として転送します。
- `LowSleepSpeed=2` は要求された 1000 ms のスリープを 2000 ms として転送します。

これらは要求された間隔であり、正確な経過時間の保証ではありません。変換は除算の前に 32 ビット符号なし演算で乗算します。大きな値はオーバーフローする可能性があり、非常に小さな結果はゼロに切り捨てられる可能性があり、任意のスケーリングは `INFINITE` などの特別なタイムアウト値を保持する必要はありません。

これは `WaitForSingleObject` などの同期待機を変更しません。実際の経過時間は、通常の Windows スケジューリング、タイマー解決動作、およびアラート可能なスリープ セマンティクスの対象のままです。

### タイマー関数 {#timer-functions}

`AddTimerSpeed` と `LowTimerSpeed` は次を制御します。

- `SetTimer`
- `timeGetTime`
- `timeSetEvent`

現在の実装では、`timeGetTime` はティック係数グループではなくタイマー係数グループに属します。`GetTickCount` とは別に、そのフックがインストールされたときに取得された独自のネイティブ参照を使用して返されたクロック値を調整します。タイマー間隔を変更しません。

演算限界内の通常の正の係数の場合、`SetTimer` と `timeSetEvent` は要求された間隔をおおよそ `LowTimerSpeed / AddTimerSpeed` で調整します。`timeGetTime` クロックは対応する `AddTimerSpeed / LowTimerSpeed` 関係を使用します。もう一方の係数を `1` にすると:

- `AddTimerSpeed=2` は要求されたタイマー間隔をおおよそ半分にし、`timeGetTime` をおよそ 2 倍速く進めます。
- `LowTimerSpeed=2` は要求されたタイマー間隔をおおよそ 2 倍にし、`timeGetTime` をおよそ半分の速さで進めます。

間隔ラッパーは 64 ビット中間演算を使用し、次にネイティブ間隔タイプに変換し直します。大きく変換された値は狭くなったりラップしたりする可能性があります。Windows のタイマー最小値、サポートされている範囲、解像度、メッセージ処理、およびスケジューリングは依然として適用されるため、実際のコールバックまたはメッセージ配信時間は計算された間隔と異なる場合があります。タイマー フックのインストールには、ランタイム スコープで説明されている追加の GUI 条件もあります。

## 係数の比較

| 設定 | 制御対象 | 値 `2` |
| ------- | -------- | --------- |
| `AddTickSpeed` | サポートされているティック/クロック ソース | 上記のクロック制限の対象で、約 2 倍速く |
| `LowTickSpeed` | サポートされているティック/クロック ソース | 約 2 倍遅く。ただし `QueryUnbiasedInterruptTime` はゼロを生成します |
| `AddSleepSpeed` | `SleepEx` の要求された期間 | 1000 ms が 500 ms として転送されます |
| `LowSleepSpeed` | `SleepEx` の要求された期間 | 1000 ms が 2000 ms として転送されます |
| `AddTimerSpeed` | サポートされているタイマー API | 要求された間隔が約半分。`timeGetTime` が速くなります |
| `LowTimerSpeed` | サポートされているタイマー API | 要求された間隔が約 2 倍。`timeGetTime` が遅くなります |

各ペアのもう一方の係数は `1` であると仮定しています。これらは要求の変換またはおおよそのクロック関係であり、上記の制限の対象です。

## 例

```ini
[DefaultBox]
UseChangeSpeed=y
AddTickSpeed=2
AddSleepSpeed=2
AddTimerSpeed=2
```

該当するフックがインストールされ、値が演算限界内にある場合、この構成は一般に次を引き起こします。

- 影響を受けるティックおよびクロック ソースがおよそ 2 倍速く進みますが、それらが 1 つの一貫したクロックになるわけではありません。
- 要求された 1000 ms のスリープが 500 ms として転送されます。
- 要求されたタイマー間隔がおおよそ半分に削減されます。
- `timeGetTime` がおよそ 2 倍速く進みます。

## Add 係数と Low 係数の組み合わせ

同じグループの Add バリアントと Low バリアントを一緒に構成できます。どちらの設定も他方を上書きしません。例:

```ini
[DefaultBox]
UseChangeSpeed=y
AddTickSpeed=2
LowTickSpeed=3
```

演算限界内で、これは `GetTickCount`、`GetTickCount64`、および `QueryPerformanceCounter` に、それらの異なる参照点を使用しておよそ `2/3` のスケーリングを適用します。`QueryUnbiasedInterruptTime` は代わりに `2` を `3` で最初に除算し、ゼロを生成します。したがって、Add 値と Low 値は、1 つの統一された式ではなく、傍受された API に従って組み合わさります。ティック、スリープ、およびタイマー係数グループは独立したままであるため、1 つのグループを変更しても他のグループが自動的に構成されることはありません。

## ランタイム スコープ

該当するフックは、Sandboxie の注入された DLL を通じてサンドボックス化されたプロセス内で実行されます。インストールは、有効な構成、初期化パス、API/モジュールの可用性、フッキングの成功、および該当するフック抑制設定に依存します。すべてのプロセスがすべてのフックを受け取るわけではありません。これは Windows クロックへのシステム全体の変更ではありません。SandMan と Sandboxie サービスは、サンドボックス外の操作では通常影響を受けません。

タイマー フックはさらに GUI の初期化に依存します。それらのインストール ブロックは、アプリケーション コンパートメントおよび有効な `NoSandboxieDesktop=y` の場合にスキップされます。ティック/クロックおよび `SleepEx` フックはこの GUI 条件を共有しません。

`UseChangeSpeed` は関連する初期化子によって読み取られます。構成を再読み込みしても、完了した初期化子が再実行されたり、タイミング フックが遡ってインストールまたは削除されたりしません。フックのインストールを確実に変更するには、影響を受けるサンドボックス化されたアプリケーションを再起動してください。まだ実行されていない GUI 初期化子は、後で新しく有効になった値を読み取る場合があります。それは再読み込みによって引き起こされる再インストールではなく、遅延初期化です。

6 つの数値係数はすべて、対応するフック呼び出し中に照会されるため、正常に再読み込みされた値はインストールされたフックに影響を与える可能性があります。係数ペアは別々に読み取られ、更新はタイミング ソース間でアトミックではなく、保持された初期化参照は変更がクロックの不連続を引き起こす可能性があることを意味します。間隔の変更は後続の傍受された呼び出しに適用されます。係数の変更だけでは既存のタイマーを再プログラムしません。ファイルを保存するだけでは、構成の再読み込みが成功したことを確立しません。通常の更新は、本質的に Sandboxie サービス、ドライバー、または Windows の再起動を必要としません。

## 意図された使用

この機能は、分析またはテスト中に固定アプリケーション遅延を削減したり、互換性のあるシングルプレイヤー アプリケーションまたはゲームの論理速度を変更したりするなどのシナリオを目的としています。互換性は、アプリケーションが使用する Windows タイミング メカニズムに依存します。CPU 実行を加速したり、プロセッサ周波数を増加させたりするものではなく、より速いアプリケーション実行やゲーム互換性を保証するものでもありません。

## 制限

- この機能は、すべての Windows 時間ソースまたは待機メカニズムを傍受しません。システム ウォール クロック API、`NtQuerySystemTime`、`NtDelayExecution`、同期待機、待機可能タイマー、タイマー キュー、およびスレッドプール タイマーはカバーされません。
- 選択された API のみが調整されるため、複数のタイミング ソースを比較するアプリケーションは一貫性のない経過時間を観察する場合があります。
- 同期待機は、スリープ係数によって一般に短縮または延長されません。
- タイミング動作の変更は、アプリケーション ロジック、応答性、メディア処理、またはタイムアウトの前提に影響を与える可能性があります。
- 小さな正の整数係数を使用してください。整数の丸め、演算限界、ネイティブ タイマー制約、およびアプリケーションのタイミング前提は、特に大きな係数または非常に短い間隔で予期しない結果を生成する可能性があります。等しい Add/Low 係数が中間オーバーフローから普遍的に保護されるわけではありません。

現在、これらの設定のための専用のグラフィカル コントロールはありません。SandMan では、**Sandbox Options > Edit ini Section > Edit ini** を使用してください。Sandboxie Control Classic では、**Configure > Edit Configuration** を使用してください。Plus と Classic は、該当する場合に関連するランタイム コードを共有します。手動構成はフックのインストールや特定のタイミング結果を保証しません。
