# Token and Syscall Internals

## 概要

通常のセキュリティ分離ボックス内のプロセスは、制限または再構築された Windows プライマリ トークンで実行されます。Sandboxie はまた、選択されたネイティブ システムコール スタブにパッチを適用し、それらの呼び出しを SbieDrv 経由でルーティングして、ドライバーが互換性のある操作を検査および仲介できるようにします。

現在のトークン構築パスのユーザー向け構成については、[Access Token Isolation](AccessTokenIsolation.md) を参照してください。

このトークンおよびシステムコール アーキテクチャは、Sandboxie の分離モデルの一部にすぎません。ファイル、レジストリ、IPC、ネットワーク、GUI、およびその他のコントロールは別々に実装されています。[Isolation Mechanism](IsolationMechanism.md) を参照してください。[No Security Isolation](NoSecurityIsolation.md) を通じて構成される Application Compartment モードは、通常ここで説明するプライマリ トークン置換モデルをバイパスします。

## 関与するコンポーネント

- **SbieDrv** はサンドボックス化されたプロセスを追跡し、そのプライマリ トークンを置き換え、ネイティブ システムコールを仲介し、関連するカーネル側のポリシーとフィルター処理を適用します。
- **SbieSvc** は初期プロセス インジェクションを調整し、特権ヘルパー機能を提供します。
- **LowLevel / SbieLow** は初期のインジェクションされたセットアップを実行し、選択されたネイティブ システムコール スタブにパッチを適用します。
- **SbieDll** はユーザー モードの仮想化、互換性フック、および関連する初期化を提供します。

## プロセスの起動

現在の高レベルの起動フローは次のとおりです:

```text
Windows process creation
    |
    v
process callback identifies sandboxed process
    |
    v
early LowLevel / SbieDll injection is coordinated
    |
    v
first relevant image-load initialization
    |
    v
Sandboxie initializes sandbox subsystems
    |
    v
primary token is filtered/reconstructed
    |
    v
restricted/reconstructed token is assigned
    |
    v
earlier source token is retained for mediated operations
```

ドライバーのプロセス コールバックがサンドボックス化されたプロセスを識別して記録し、SbieSvc が低レベル インジェクションを調整します。最初の関連するイメージ読み込み通知が、サンドボックス サブシステムおよびプライマリ トークン置換パスの初期化をトリガーします。

## プライマリ トークン処理

トークン処理には別個の段階があります:

```text
original primary token
    |
    v
preliminary filtering
    |
    v
restriction / reconstruction
    |
    v
sandbox primary token
```

予備フィルター処理は、後の制限または再構築段階の前にトークン プロパティを削除または無効化することがあります。その結果、その後の段階に提供されるトークン、および置換後に保持される以前のソース トークンは、既に予備的にフィルター処理されている可能性があります。高度な構成はどの段階が使用されるかを変更できますが、保持されたトークンを普遍的に元の無制限トークンとして説明すべきではありません。

`SeFilterToken` は現在の予備フィルター処理段階で使用されます。これはレガシ制限パスで使用される内部 `SepFilterToken` ルーチンとは別個で、レガシ専用ではありません。

## 最新のトークン再構築

現在の通常の構成では、一般に `Token_CreateToken` を使用します。このパスは、`SepFilterToken` が利用できない場合、`UseCreateToken` がそれを選択する場合、または `SandboxieAllGroup` がそれを選択する場合に選択されます。`SandboxieAllGroup` の現在のランタイム既定により、最新の再構築が一般的な通常パスになります。

最新のパスは、ソース トークン オブジェクトをその場で変更するのではなく、ソース トークン情報から新しいトークンを構築します。トークン ユーザー、グループ、特権、整合性、所有者、プライマリ グループ、既定の DACL、トークン ソース、認証およびトークン統計、および該当する場合はデバイス グループとトークン セキュリティ属性を処理します。通常の再構築は、トークン ユーザーを置き換え、整合性を下げ、グループを制限し、特権を減らし、Sandboxie 固有のトークン グループを追加できます。

最新の再構築パスは、動的に解決されたトークン作成サービスを通じて新しいトークンを既に作成しており、`ZwCreateTokenEx` を優先し、必要な場合は `ZwCreateToken` にフォールバックします。これらは通常のユーザー向け構成 API ではなく、内部カーネル サービスです。

## レガシ トークン フィルター処理

古い制限トークン パスは実装に残っています。これは、`SepFilterToken` が解決され、最新のパスが選択されず、高度な構成が制限段階をバイパスしなかった場合に選択できます。

レガシ パスは、内部的に解決された `SepFilterToken`、文書化された `SeFilterToken`、および `RestrictedSidCount`、`RestrictedSids`、`UserAndGroups`、`UserAndGroupCount` などの内部 `TOKEN` 構造体情報を使用します。レガシ トークン パスは依然として `SepFilterToken` および内部 `TOKEN` レイアウト データを使用しますが、現在の構成では通常のパスではありません。

## 保持されたソース トークン

プライマリ トークンの置換が成功した後、Sandboxie はプロセスごとの状態で以前のソース トークンへの参照を保持します。予備フィルター処理に応じて、これは元のプライマリ トークンまたは予備的にフィルター処理されたソース トークンである可能性があります。

仲介された呼び出しのために、Sandboxie は記録されたスレッド インパーソネーション トークンまたは保持されたプロセス ソース トークンを一時的に偽装することがあります。一時的な偽装は通常、操作後にクリアされます。

Sandboxie の現在のインパーソネーション ヘルパーは `SecurityIdentification` で `PsImpersonateClient` を呼び出します。より高い有効な偽装レベルが必要な場合、DynData を通じて提供されるバージョン固有の `ETHREAD` 情報を使用してそのレベルを調整します。これは、単なる歴史的な Windows XP のワークアラウンドではなく、サポートされている Windows バージョンに対する現在の実装固有の依存関係のままです。

## ネイティブ システムコール仲介

Sandboxie は関連するネイティブ システムコール エクスポートとスタブを列挙します。インジェクションされた低レベル コードは選択されたスタブにパッチを適用し、呼び出しを SbieDrv 経由でルーティングします。ドライバーはシステムコール エントリを識別し、存在する場合は Sandboxie 固有のハンドラーを適用するか、適切に基になるカーネル サービスを呼び出します。通常の仲介中、上記の一時的なソース トークンまたはスレッド トークンの偽装を適用し、その後その偽装をクリアすることがあります。

ドライバーのシステムコール メタデータには、システムコールまたはサービス インデックス、カーネル サービス アドレス、引数カウント、およびハンドラーまたは承認状態が含まれます。アドレスと引数カウントの情報は依然としてサービス テーブル メタデータから導出されます。ネイティブ NT システムコールと Win32k システムコールは関連しているが別個のメカニズムを使用します。Win32k サポートは条件付きで、別個のディスパッチ構造体を持っています。

サービス テーブル情報は、DynData、利用可能な場合はエクスポートされた `KeServiceDescriptorTable`、および `KeAddSystemServiceTable` を含むアーキテクチャまたはビルド固有の分析など、いくつかの経路から取得できます。したがって、Sandboxie が常に `KeAddSystemServiceTable` のみを分析して単一の非エクスポート テーブルを特定するという歴史的な説明は不完全です。

## 直接システムコール

パッチ適用された NTDLL スタブをバイパスする直接システムコールは、その特定のユーザー モードからドライバーへの仲介経路もバイパスします。ただし、Sandboxie の保持されたソース トークン コンテキストを回復するものではありません。呼び出しは通常、制限または再構築されたサンドボックス プライマリ トークンの下で実行され、適用可能な Windows アクセス チェックおよび独立した Sandboxie カーネル強制の対象のままです。

正確な結果は、システムコール、トークンのアクセス許可、アクティブな Sandboxie サブシステム、および構成によって異なります。したがって、直接システムコールはすべての Sandboxie コントロールをバイパスするのでも、1 つの普遍的な失敗結果を持つのでもありません。

Application Compartment モードでは、プライマリ トークン置換は通常バイパスされ、このメカニズムで使用される保持されたプロセス トークンは通常のパスを通じて確立されず、低レベルのシステムコール フックはそのモードでは無効になります。SbieDll は依然として他の仮想化および互換性機能を提供できます。

## プライマリ トークン置換

イメージ読み込みコールバックは関連するプロセス初期化をトリガーしますが、それ自体でトークン ポインターを上書きするわけではありません。Sandboxie はまず置換トークンを準備します。割り当て中、プロセスの `PrimaryTokenFrozen` フラグを一時的にクリアし、`ProcessAccessToken` を指定して `ZwSetInformationProcess` を呼び出し、その後フラグを復元します。

`PrimaryTokenFrozen` へのアクセスは、該当するシステム上で DynData を通じて提供されるバージョンおよびビルド固有の `EPROCESS` 知識を使用します。Sandboxie はプライマリ トークン ポインターを直接置き換えません。

## 実装固有のカーネル依存関係

Sandboxie は、文書化された API、動的に解決されたルーチン、およびビルドに敏感な実装固有のカーネル メカニズムを組み合わせて使用します。

| 依存関係 | 役割と現在のスコープ |
| --- | --- |
| `ZwCreateTokenEx` / `ZwCreateToken` | 現在の最新再構築パスで使用される動的に解決されたトークン作成サービス。 |
| `SepFilterToken` および内部 `TOKEN` レイアウト | レガシ トークン パスで使用されます。最新パスはこれらのレガシ レイアウト依存関係を回避します。 |
| サービス記述子テーブル情報 | システムコール仲介のためのネイティブ サービス、アドレス、および引数メタデータを識別するために使用されます。 |
| `ETHREAD` 偽装情報 | 有効な偽装レベルを調整するときに現在のインパーソネーション ヘルパーで使用されます。 |
| `EPROCESS` プロセス情報 | プロセス初期化に関与する `PrimaryTokenFrozen` およびその他のビルドに敏感なフィールドを含みます。 |

Sandboxie には、このトークンおよびシステムコール パスの外側にも、クリップボードおよびウィンドウ ステーションの処理など、ビルドに敏感なカーネル互換性コードが含まれています。

## 動的データ

DynData は、実装に敏感なカーネル構造体およびサービス テーブルに関するビルド固有の知識を提供します。ドライバーは、新しいビルド用に組み込みデータまたは受け入れられた署名済み外部データを使用できます。

互換性のある DynData が利用できない場合、ドライバーは読み込まれたままにできますが、影響を受けるボックスは通常のトークン分離を受ける代わりに Application Compartment 動作を強いられる可能性があります。したがって、DynData の欠落は 1 つの普遍的なフェイルクローズまたは起動失敗の結果を持ちません。

## 失敗時の動作

必要なソース トークンの取得、必須のサンドボックス トークンの構築、または置換トークンの割り当てに失敗すると、プロセスの初期化が中止される可能性があります。`SepFilterToken` の解決に失敗すると最新の構築パスが選択され、`ZwCreateTokenEx` が利用できない場合は `ZwCreateToken` にフォールバックできます。

ネイティブまたは Win32k システムコール初期化中の失敗は、ドライバーの初期化を妨げる可能性があります。必要な一時的な偽装の確立に失敗すると、影響を受けるサンドボックス化されたプロセスが終了する可能性があります。上記のように、互換性のある DynData が利用できない場合は、代わりにコンパートメント モードのフォールバックが発生することがあります。これらのパスは 1 つの普遍的な失敗ポリシーとして要約すべきではありません。

## 歴史的な進化

元のアーキテクチャは、レガシ `SepFilterToken` / `SeFilterToken` パスを内部 `TOKEN` オフセットとともに使用していました。Sandboxie Plus 1.0.7 / Classic 5.55.7 時代の開発で、実験的な `CreateToken` ベースの再構築が導入されました。2022 年 1 月 2 日までに、ソースには既に `ZwCreateToken` フォールバック付きの `ZwCreateTokenEx` を使用する `SbieCreateToken` が含まれていましたが、2022 年後半に作成されたこのページの元のバージョンは、その変更を将来の方向性として依然として議論していました。

Sandboxie Plus 1.13.0 / Classic 5.68.0 が署名済みで更新可能な DynData アーキテクチャを導入しました。バージョン 1.14.1 / 5.69.1 が最新の `UseCreateToken` / `SandboxieAllGroup` パスを統合し、バージョン 1.17.0 / 5.72.0 が `SandboxieAllGroup` をランタイム既定で有効にしました。その変更により、古いパスをそれを選択する構成およびシステム用に保持しつつ、最新のトークン再構築が一般的な通常パスになりました。
