# ファイル仮想化と ID

Sandboxie の通常のファイルシステム仮想化は、ファイルの内容とメタデータが異なるバッキング レイヤーから取得される可能性がある一方で、論理ファイル パスを提示します。有用な概念的なルックアップ順序は次のとおりです。

```text
live sandbox state
    |
    v
active snapshot
    |
    v
parent snapshots
    |
    v
host or other resolved backing
```

削除および再配置の状態は、下位レイヤーを抑制またはリダイレクトできます。アクセス ルールは、通常のマージされた仮想化を別のモードに置き換えることができ、すべての Windows API が同一のパスに従うわけではありません。これはルックアップ モデルであり、不変の物理ディレクトリ レイアウトではありません。

## 論理パスとサンドボックス ストレージ

サンドボックス化されたアプリケーションは通常、その論理パスを引き続き使用しますが、ライブ サンドボックス内に作成または移行されたファイルは、有効なファイル コンテナー ルートの下に物理的に保存されます。したがって、論理ファイルとそのサンドボックス表現は異なるボリューム上に存在する場合があります。ストレージ構成については、[サンドボックス ルートとボリューム レイアウト](SandboxRootsVolumeLayout.md)と[ファイル ルート パス](FileRootPath.md)を参照してください。

選択された傍受されるファイル名および最終パスのクエリは、サンドボックス バッキングのハンドルをアプリケーションの論理パスに向けて変換し直します。これは、すべての API が物理サンドボックス パスを隠すことを保証するものではありません。

## ファイルの読み取り、作成、および変更

ライブ サンドボックス表現がパスを覆い隠していない場合、対象となる読み取り専用オープンは、最初にライブ サンドボックスにコピーすることなく、解決されたバッキング オブジェクトを直接使用できます。そのバッキングは、ホスト ファイル、スナップショット、または別の解決済みまたは再配置されたソースにすることができます。アクセス モード、削除状態、スナップショット、および互換性パスは結果を変える可能性があり、すべての読み取りがこの直接パスを使用するわけではありません。

可変のサンドボックス ローカル状態を必要とする操作は、一般にライブ表現を必要とします。既存のバッキング ファイルの場合、Sandboxie は操作を完了する前に情報をその表現に移行する場合があります。可視の下位バッキングを持たない新しい論理ファイルの場合、通常の仮想化パスは対応するホスト ファイルを作成するのではなく、サンドボックス ストレージ内にオブジェクトを作成します。

使用可能なライブ表現が存在すると、通常の仮想化アクセスのために、対応する下位レイヤーのオブジェクトを覆い隠します。ライブ ファイルは関連する操作のために独自の内容とメタデータを提供し、Sandboxie はそのバイトを下位ファイルのバイトとマージしません。メタデータ クエリのフォールバック動作は、すべての API で同一ではありません。

## 移行の決定

移行は常に完全な内容のコピーであるとは限りません。操作とポリシーに応じて、Sandboxie は既存のデータを含むコピー、以前の内容を含まない表現、メタデータまたはディレクトリ状態、または特殊な再解析ポイント状態を作成する場合があります。例:

- 通常の変更は、既存の内容のコピーを必要とする場合があります。
- 上書きは、古い内容を最初に保持せずにメタデータを保持できます。
- 削除時クローズ付きの削除のみのオープンは、ファイル内容のコピーを避けることができます。
- ディレクトリ表現の作成は、その子を再帰的にコピーしません。

ストリームと再解析ポイントには特殊な処理があり、このモデルはすべてのオブジェクト タイプが同一にコピーされるという約束ではありません。

完全な内容の移行が検討されている場合、移行ルールと現在のサイズ/プロンプト ポリシーが、Sandboxie が内容をコピーするか、空の表現を作成するか、移行を拒否するか、該当するフォールバックに従うかを決定します。[ファイル移行設定](FileMigrationSettings.md)は構成をカバーし、[常にコピー](CopyAlways.md)、[空をコピー](CopyEmpty.md)、および[コピーしない](DontCopy.md)は個々の移行ルールを説明します。[新しい方をコピー](CopyNewer.md)は、既存のライブ コピーのための別個の更新メカニズムです。

Sandboxie が要求されたコンテンツ移行を拒否した場合、[コピー ブロック書き込み拒否](CopyBlockDenyWrite.md)は、そのパスを拒否するか、Sandboxie が書き込み/削除機能を削除して解決されたバッキングを再試行できるかを決定します。縮小アクセスの再試行は依然として失敗する可能性があり、バッキングは現在のホスト ファイルではなくスナップショットまたは再配置されたソースである場合があります。この拒否処理は、すべての移行エラーのフォールバックではありません。

表現の作成またはデータの移行は失敗する可能性があります。ネイティブのアクセス許可と共有動作は依然として関連しており、移行は失敗後にすべての中間ファイルシステム変更をロールバックする普遍的なトランザクションではありません。

## マージされたビュー、削除、およびスナップショット

ディレクトリ列挙は、ライブ サンドボックス状態、スナップショット レイヤー、およびホスト/バッキング レイヤーからのエントリを結合できます。同じ論理名の場合、通常は上位の可視レイヤーが優先されます。削除状態は、その下にまだ物理的に存在するエントリを抑制できます。結果として得られるマージされたビューにより、ストレージが分散していても、アプリケーションは 1 つの論理名前空間を使用できます。

通常の仮想化されたサンドボックス内で既存のホスト バッキング ファイルを削除しても、ホスト オブジェクトを削除する必要はありません。Sandboxie は、下位オブジェクトがサンドボックス化されたビューで存在しないように見せるサンドボックス側の状態を記録します。V1 と V2 はその状態を異なる方法で保存します。[仮想化スキーム V1 と V2](Delete-V2.md)を参照してください。これは、すべてのメタデータ API を通じて同一の削除可視性を約束するものではありません。

[ボックス スナップショット](../PlusContent/BoxSnapshots.md)では、ライブ変更はアクティブなスナップショットの上に位置し、その親スナップショットが古いバッキングを提供できます。ホストまたはその他の解決されたバッキングは、上位の可視状態が論理オブジェクトを提供または抑制しない場合にのみ到達されます。スナップショット バッキングのオブジェクトを変更すると、新しいライブ表現が作成または移行される場合があります。スナップショットの管理とクリーンアップのワークフローは、スナップショット ページに文書化されています。

## 実効的なファイル アクセス モード

| 実効モード | アーキテクチャ上の結果 |
| --- | --- |
| [Normal](NormalFilePath.md) | 通常のマージされた仮想化を使用します。下位バッキングを読み取ることができ、可変状態はサンドボックス側に保持されます。 |
| [Open](OpenFilePath.md) | 一致する操作に対して、通常のコピー仮想化ではなく真の/ホスト パスに直接アクセスします。 |
| [Closed](ClosedFilePath.md) | 通常のコピー パスの前に一致する論理アクセスを拒否します。 |
| [Read](ReadFilePath.md) | 読み取り指向モードのために直接真のパス アクセスを使用し、該当する書き込み強制は別個のままです。 |
| [Write](WriteFilePath.md) | 通常の下位バッキング データを隠し、サンドボックス/コピー側で操作します。 |

これらは、有効なルールが選択された後の高レベルの効果です。ルールの優先順位とネストされた例外は、[ルールの特異性](../PlusContent/RuleSpecificity.md)で別途文書化されています。Closed アクセスは、考えられるすべてのメタデータ クエリを見えなくするものとして解釈すべきではなく、これらのモードは Windows ACL アクセス許可を付与またはバイパスしません。

仮想化は、論理状態がどこで読み取られるか、または保存されるかを決定します。Sandboxie のアクセス ポリシーは、許可される操作と通常の仮想化が適用されるかどうかを決定します。Windows/ファイルシステムのアクセス許可は、物理オブジェクトへのネイティブ アクセスを管理します。コピーオンライトだけでは完全なセキュリティ境界ではありません。

## ファイル ID と File ID

1 つの論理ボリューム上に提示されるファイルは、物理的には別のボリューム上のサンドボックス ストレージに存在する場合があります。あらゆる場所で生の物理 File ID を返すと、ID と ID によるオープンの動作がその名前空間と矛盾する可能性があります。したがって、Sandboxie は選択されたクエリ パスで ID を調整し、サポートされている ID によるオープンのケースに対して逆の処理を行います。これは互換性と ID の処理であり、アクセス許可の強制、暗号化、または匿名化ではありません。

### クエリ カバレッジとバッキング ID

File ID 仮想化は部分的であり、API に依存します。選択されたハンドル ベース、名前ベース、およびマージされたディレクトリのクエリ パスは、仮想化されたビューの一部として ID を調整できますが、カバレッジはすべての Windows 情報クラスまたは列挙パスで一様ではありません。現在の処理は、`FileInternalInformation`、`FileAllInformation`、`FileIdInformation`、`FileStatInformation`、`FileStatLxInformation`、および `FileStatBasicInformation` を含む File ID を持つ形式を認識します。この一覧は、すべてのクエリ API がすべての形式を受け入れる保証ではありません。

カバーされるハンドル クエリ パスでは、直接ホスト ハンドルは通常そのネイティブ File ID を保持しますが、ライブまたはスナップショット バッキングのボックス化されたハンドルは Sandboxie の調整された ID を受け取る場合があります。新しく作成されたサンドボックスのみのファイルは、独自の物理ファイルシステム オブジェクトからその ID を導出します。Sandboxie はそれにグローバルに合成されたパス ベースの ID を割り当てません。移行は、ホスト ファイルの以前の ID を保持することを約束しません。

ディレクトリ列挙 ID は、すべてのハンドル ベースまたは名前ベースのクエリによって返されるものと同一であると仮定すべきではありません。現在の列挙パスは普遍的なクロス API ID 保証を提供しません。すべてのホスト エントリがネイティブのままであること、またはすべてのエントリが変換されることのいずれも安全な仮定ではありません。

### 安定性と ID によるオープン

変換は基になる ID に対して決定的ですが、Sandboxie は論理パスごとに別個の永続的な合成識別子を割り当てません。再作成、移行または CopyNewer 置換、スナップショット切り替え、サンドボックス ストレージの移動または再作成、ホストへの復元、またはファイルシステム変更をまたいで ID が安定したままであることに依存しないでください。プロセス、SandMan、またはサービスの再起動は、このメカニズムに新しいランダム ID シードを導入しません。

サポートされている ID によるオープン パスの場合、Sandboxie は ID 解決を再試行し、結果を論理パスに変換し直すことができ、その後通常のサンドボックス パス/ルール処理が適用されます。これはファイル ルールまたは Windows アクセス チェックをバイパスしたり、最初にクエリされた同じ物理スナップショット レイヤーを再度開くことを保証したりしません。

現在の処理は、すべてのファイルシステムとクエリ ファミリにわたる普遍的な 128 ビット File ID ラウンドトリップ セマンティクスを確立しません。特に、識別子の上位部分が重要である場合にそうです。アプリケーションは、すべての File ID API が 1 つの完全に合成された相互に交換可能な ID を公開すると仮定すべきではありません。

### ボリューム情報

File ID の調整とボリューム情報は別個のメカニズムです。一部のファイル メタデータは依然として物理バッキング ボリュームを反映する場合があり、選択されたボリューム クエリは論理ドライブに向けてリダイレクトされる場合があります。Sandboxie は完全に合成されたファイルシステム ボリューム ID を提供しません。

## 構成変更の適用とライフサイクル

ライブで移行または作成されたファイルシステム状態は、関連するワークフローを通じて変更、削除、またはリセットされるまでサンドボックス ストレージに保持されます。削除およびスナップショット状態も永続的なサンドボックス状態であり、独自のメカニズムの対象です。

移行ルールと制限は、サンドボックス化されたプロセスのために初期化およびキャッシュされます。新しい値が使用されるように、それらの設定を変更した後は影響を受けるサンドボックス化されたプロセスを再起動してください。これは、すべての移行関連の決定がキャッシュされることを意味するものではありません。既存のオープン ハンドルは、構成変更によって再ターゲットされるのではなく、すでに開いたオブジェクトを参照し続けます。File ID 変換自体は SandMan の再起動を必要としません。
