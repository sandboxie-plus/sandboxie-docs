# SandMan トリガー

SandMan は、選択されたサンドボックス イベントに応答して自動的に実行されるコマンドをサポートします。次の設定がこのメカニズムを使用します。

* `OnBoxDelete`
* `OnBoxTerminate`
* `OnFileRecovery`

> **セキュリティ上の注意:** SandMan トリガーは、ユーザーが構成した信頼済みの管理自動化です。`SandMan.exe` はホスト上で、イベントを引き起こしたサンドボックスの外側でそれらのコマンドを起動します。

トリガー コマンドは、サンドボックス化されたアプリケーションへのコールバックではありません。それらは SandMan の現在のユーザーおよびセキュリティ コンテキストで実行され、自動的に昇格されません。SandMan がすでに昇格している場合、コマンドはその昇格したコンテキストを継承します。発信元サンドボックスに適用された制限（その `StartRunAccess` ルールなど）は、ホスト側のコマンドを封じ込めません。

## 構成

```ini
OnBoxDelete=<command line>
OnBoxTerminate=<command line>
OnFileRecovery=<command line>
```

各設定は繰り返すことができます。コマンドは構成によって返される実効順序で順次実行されます。複数のテンプレートと `GlobalSettings` から継承されたエントリ間の特定の順序に依存しないでください。

例:

```ini
OnBoxTerminate="C:\Tools\box-audit.exe" --box "%BoxName%"
OnBoxTerminate="C:\Tools\cleanup-log.exe" "%BoxPath%"
```

便利な Sandboxie 展開には次が含まれます。

* `%SbieHome%` — Sandboxie のインストール ディレクトリ
* `%BoxPath%` — サンドボックスのファイル ルート
* `%BoxName%` — サンドボックス名

通常の Sandboxie 構成展開は、他のサポートされている `%...%` 変数にも適用されます。関連する構成の概念については、[展開可能な変数](ExpandableVariables.md)を参照してください。

SandMan は構成されたコマンド ラインを直接起動します。暗黙の `cmd.exe` シェルはないため、バッチ ファイルとシェル演算子は、該当する場合は明示的なコマンド インタープリターを必要とします。

```ini
OnBoxDelete=cmd.exe /c "C:\Scripts\cleanup.cmd"
```

スペースを含む実行可能ファイル パスは引用符で囲む必要があります。コマンドは SandMan の環境と現在の作業ディレクトリを継承します。Sandboxie インストール ディレクトリなど、特定の作業ディレクトリを仮定しないでください。

## OnBoxDelete

`OnBoxDelete` は、SandMan がサンドボックスの内容をクリーンアップする前に、構成されたホスト側のコマンドを実行します。これは次に適用されます。

* 手動の **Delete Contents** 操作
* [AutoDelete](AutoDelete.md) クリーンアップ
* 同等の SandMan コンテンツ クリーンアップ操作
* サイレントまたは非同期のクリーンアップ パス

サンドボックス定義自体の削除は、通常このトリガーを呼び出しません。`OnBoxDelete` は、サンドボックス構成の削除ではなく、コンテンツ クリーンアップ前の自動化を表します。

AutoDelete がボックスの終了に続く場合、関連する順序は次のとおりです。

1. `OnBoxTerminate` が最初に実行されます。
2. SandMan が復元処理を提供する場合があります。
3. クリーンアップが続行する場合、`OnBoxDelete` が実行されます。
4. SandMan が結果として得られるスナップショット認識クリーンアップ アクションを実行します。

AutoDelete の復元がクリーンアップ開始前にキャンセルされた場合、`OnBoxTerminate` はすでに実行されている可能性がありますが、`OnBoxDelete` は実行されません。

`OnBoxDelete` は、SandMan がスナップショット認識クリーンアップを実行する前に実行されます。クリーンアップの選択と構成に応じて、SandMan はアクティブなスナップショット状態に戻るか、既定のスナップショット状態に戻るか、スナップショットが削除されるときに完全なクリーンアップを実行する場合があります。トリガーはスナップショット情報を自動的に受け取りません。一般的なスナップショット動作については、[ボックス スナップショット](../PlusContent/BoxSnapshots.md)を参照してください。

`OnBoxDelete` は Sandboxie Plus 1.0.10 以降で利用可能です。

## OnBoxTerminate

`OnBoxTerminate` は通常、アクティブなプロセスを持っていたサンドボックスが残りのアクティブなプロセスを持たなくなったことを SandMan が観測したときに実行されます。個々のプロセスの終了ごとに実行されるわけではありません。

```text
active process count > 0
        ↓
active process count = 0
        ↓
OnBoxTerminate
```

これは次の後に発生する可能性があります。

* 最後のプロセスが自然に終了した
* **Terminate All** の後、すべてのプロセスが実際になくなったとき
* ボックスを空のままにする強制終了

ボックスが後でプロセスを起動し、再び空になった場合、トリガーは再び実行される可能性があります。`LingerProcess` と `LeaderProcess` は直接それを発火させませんが、ボックスが最終的にアクティブ プロセス ゼロに達する時期に影響を与えることがあります。

`OnBoxTerminate` は SandMan の AutoDelete 処理の前に実行されます。トリガーの終了ステータスを AutoDelete の前提条件として扱うべきではありません。

エッジ ケースとして、SandMan の起動時クリーンアップ モードは、すでに空のボックスに対してボックス クローズ処理を呼び出すことがあり、これも `OnBoxTerminate` の実行を引き起こす可能性があります。

`OnBoxTerminate` は Sandboxie Plus 1.13.1 以降で利用可能です。

## OnFileRecovery

ファイルごとに、`OnFileRecovery` は、SandMan がそのファイルをホストの復元先に移動しようとする前に、構成されたチェッカー コマンドを実行します。これはファイルごとのチェックであり、完全な復元操作後のコールバックではありません。

SandMan は構成されたコマンドを展開し、サンドボックス ストレージ内のファイルの引用符で囲まれた物理パスを追加します。例:

```ini
OnFileRecovery="C:\Tools\scan.exe" --check
```

は概念的に次のように実行されます。

```text
"C:\Tools\scan.exe" --check "<physical sandbox file path>"
```

構成されたコマンドにすでに引数が含まれている場合、サンドボックス ファイル パスは最後に自動追加される引数です。SandMan は復元先、復元方法、またはボックス名を自動的に追加しません。チェッカーがボックス名を必要とする場合は `%BoxName%` を使用できます。

チェッカーは、SandMan の通常の復元エンジンを使用する復元操作に適用されます。これには次が含まれます。

* 通常および[クイック復元](QuickRecovery.md)のフロー
* Auto/Instant Recovery プロンプトからの復元
* SandMan のファイル ビューから開始された復元

これは、SandMan の復元エンジンを使用しない外部のドラッグ アンド ドロップまたはその他のメカニズムのカバレッジを保証するものではありません。

終了コード 0 は復元の続行を許可します。ゼロ以外の終了コードまたはチェッカーの起動失敗は、SandMan にファイルをそれでも復元するかスキップするかを尋ねさせます。決定は現在の操作の残りのファイルに適用できます。すでに復元されたファイルはロールバックされません。

したがって、チェッカーはユーザー支援の互換性および安全性のステップであり、必須のセキュリティ境界ではありません。長時間実行されるチェッカーは復元操作を遅延させる可能性があります。

`OnFileRecovery` は Sandboxie Plus 1.7.0 で導入されました。現在の設定メタデータは 1.4.0 と記載していますが、ソース履歴と変更ログは 1.7.0 をその導入として識別しています。

## 失敗時の動作

トリガーの失敗処理は一様ではなく、トランザクション ポリシー メカニズムとして扱うべきではありません。

`OnBoxDelete` と `OnBoxTerminate` では、ゼロ以外のコマンド終了コードがクリーンアップ、終了、または後続の AutoDelete アクションをキャンセルすると仮定しないでください。これらのトリガーは強制ではなく自動化を目的としています。後でクリーンアップが失敗した場合、すでに実行されたコマンドはロールバックされません。

`OnFileRecovery` は、その結果が復元ワークフローによって明示的に考慮され、ユーザーが影響を受けるファイルを続行またはスキップできるため、異なります。

## 継承、インポート、および構成の信頼

トリガー エントリは、サンドボックス セクション、有効なテンプレート、または `GlobalSettings` から取得できます。SandMan は継承されたトリガー エントリを無効にすることもできます。保存された変更は一般に次の対応するイベントに適用されます。トリガー定義が変更されたという理由だけでサンドボックス化されたアプリケーションを再起動する必要はありません。操作がすでにそのコマンド リストをキャプチャした後に行われた変更は、その実行中の操作を変更しません。

> **信頼できないソースからの構成をインポートまたは有効にするときは、トリガー設定を確認してください。これらのエントリは SandMan を通じてホスト側のコマンドを起動できるためです。**

インポートされたサンドボックス構成は、別のソースから受け取ったテンプレートと同様に、トリガー設定を含む場合があります。これは、構成のインポートが定義上安全でないという意味ではありませんが、有効化または使用する前にそのトリガー エントリを確認することが重要になります。インポート情報については、[ボックスのインポート](ImportBox.md)を参照してください。

通常の[構成保護](ConfigurationProtection.md)は、誰が Sandboxie 構成を変更できるかを制限できます。任意のインポートされたコマンドを信頼できるものにするわけではありません。

## SandMan インターフェイス

コントロールは次の場所にあります。

**Sandbox Options > Advanced Options > Triggers**

現在のユーザー向けアクションは次のとおりです。

* **On Delete Content** — **Run Command**
* **On Box Terminate** — **Run Command**
* **On File Recovery** — **Run File Checker**

SandMan は自由形式のコマンド ラインを受け入れ、複数のエントリをサポートします。

## Sandboxie Plus と Classic

`OnBoxDelete`、`OnBoxTerminate`、および `OnFileRecovery` は現在 SandMan によって消費されています。同じ Sandboxie 構成ファイルを共有しても、Sandboxie Control Classic がそれらを実行することはなく、Classic はこれらの SandMan トリガーに対する同等のサポートを提供しません。

`OnBoxDelete` は SandMan の最新のクリーンアップ前トリガーです。レガシー [DeleteCommand](DeleteCommand.md) 設定は、Sandboxie Control Classic と `Start.exe` によって引き続き使用され、そこでディレクトリ削除を実行するコマンドを選択します。

2 つの設定は同等ではありません。

* `OnBoxDelete` は SandMan クリーンアップ前にユーザー構成の自動化を実行します。
* `DeleteCommand` は、準備されたサンドボックス ディレクトリを削除するために Classic と `Start.exe` が使用するレガシー削除コマンドを選択します。
