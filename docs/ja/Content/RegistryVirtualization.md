# レジストリ仮想化

Sandboxie は、ホスト レジストリの完全に独立したクローンを維持しません。通常の仮想化は、レジストリ アクセス ルールと削除または再配置の状態を使用してアプリケーションのビューを構築することにより、サンドボックス レジストリ変更を対象となるホスト データと結合します。

SbieDll は、主要な論理パス マッピングとサポートされているマージ操作を実行します。SbieDrv は別個のレジストリ フィルタリングを提供し、SbieSvc と共にサンドボックス ハイブのマウント ライフサイクルを管理します。SandMan はこれらのメカニズムを構成しますが、アプリケーション レジストリのマージは実行しません。

## レジストリ ルートと RegHive

レジストリのマウント場所とそのバッキング ファイルは異なります。

| 場所 | 目的 |
| --- | --- |
| [`KeyRootPath`](KeyRootPath.md) | サンドボックス ハイブがマウントされるレジストリ名前空間。 |
| `FileRootPath\RegHive` | サンドボックス ファイル ルートの下の物理バッキング ファイル。 |

どちらかのルートを変更しても、既存のサンドボックス内容が自動的に移行されることはありません。ルート構成とレイアウトについては、[サンドボックス ルートとボリューム レイアウト](SandboxRootsVolumeLayout.md)を参照してください。

[イメージ バッキング ストレージ](UseFileImage.md)は、サンドボックス ファイル ルート、したがって `RegHive` を運ぶ物理ストレージを変更できますが、`KeyRootPath` はハイブがマウントされるレジストリ名前空間のままです。

## 論理およびサンドボックス レジストリ パス

アプリケーションは、論理ホスト スタイルのレジストリ名を引き続き使用します。Sandboxie は、マウントされたハイブの下に対応するサンドボックス状態をマップします。例:

```text
\REGISTRY\MACHINE\Software\Vendor
    -> <KeyRootPath>\machine\Software\Vendor
```

HKLM はサンドボックスの `machine` ブランチに対応します。HKCU の場合、ホスト側の現在のユーザー SID はサンドボックスの `user\current` ブランチに対応します。ファイルシステムの `SeparateUserFolders` オプションは、このレジストリ マッピングを変更しません。

HKCR は Windows の Classes ビューであり、1 つの独立した均一な Sandboxie ルートではありません。Windows のマシン/ユーザーごとの Classes マージと、Sandboxie のサンドボックス側 Classes マッピングは別個の関係です。サンドボックスのカスタマイズは、サンドボックス ハイブ内で `user\current\software\classes` を `user\current_classes` にリンクできます。

## キーの読み取りと書き込み

通常の仮想化では、既存のホストのみのキーの読み取り専用オープンは、対応するサンドボックス キーを最初に作成せずにホスト キーを使用できます。作成操作は、要求されたアクセスが読み取り指向であっても、代わりにサンドボックス側の構造を作成できます。

通常の作成および書き込み可能なオープン操作は、ホスト キーを変更せずに、サンドボックス ハイブ内に関連する階層を実体化できます。これは、すべてのホスト値、ホスト サブツリー全体、または正確なホスト セキュリティ記述子を複製するものではありません。ホストの存在は、論理的な作成/オープンの結果に依然として影響する場合があります。

最初にホスト読み取りのために開かれたハンドルを介した値の書き込みは、ネイティブ書き込みが拒否されたときに、サンドボックスの書き込み可能パスを介して再試行できます。これは条件付き処理であり、すべての失敗した操作が再試行されるという約束ではありません。

## マージされたキーと値

サンドボックス キーは、ホスト カウンターパートの完全なコピーではなく、サンドボックス変更のみを含む場合があります。

```text
logical registry key
    +-- sandbox hive keys and values
    +-- eligible host keys and values
    +-- deletion / relocation state
```

これは、選択されたサポートされているレジストリ データ操作を表し、すべてのレジストリ API によって使用される普遍的な合成オブジェクトではありません。

- サンドボックスのみの値は、サンドボックス ビューで可視です。
- 対象となるホストのみの値は、選択されたアクセス モードが許可する場合に可視のままです。
- 同名のサンドボックス値は、マージされた結果で優先されます。
- サポートされているサブキー列挙は、ホストとサンドボックスの名前を組み合わせ、同名のエントリを統合できます。
- 認識された削除状態は、ホスト キーまたは値を抑制できます。

レジストリ クエリは、操作と情報クラスに依存します。開かれたオブジェクトからネイティブ情報を返すものもあれば、論理キー名を合成するものもあり、選択された完全/キャッシュされた情報はマージされたビューから計算されます。列挙は両方のレイヤーの 1 つのアトミック スナップショットではなく、メタデータはすべての API で一様ではありません。

## 削除と名前変更の状態

レジストリ V1 は `RegHive` 内に削除マーカーを保存し、キーと値で異なるマーカーを使用します。レジストリ V2 は、サンドボックス ファイル ルートの下の `RegPaths.dat` を使用して、通常のサンドボックス レジストリ データと共に論理キー/値の削除とキー再配置の状態を記録します。[仮想化スキーム V1 と V2](Delete-V2.md)を参照してください。

レジストリ V2 は、Sandboxie のサンドボックス化されたキー名変更処理で使用されるパス状態/再配置メカニズムを提供します。これは、すべての名前変更が成功する、またはアトミックであるという保証ではありません。V1 にはその再配置メカニズムがありませんが、これはすべてのネイティブ名前変更が失敗することを意味するものではありません。

レジストリ内容を再作成すると、新しいサンドボックス データが再び可視になる場合がありますが、削除状態とメタデータの処理は API に依存します。特に V2 ではそうです。再作成を、以前のホスト ビューの正確な復元として依存しないでください。

サンドボックス プロセスは V2 パス状態データを読み込み、`RegPaths.dat` への後続の一部の変更を検出できます。これらの更新は、トランザクション的、すべてのプロセス間で即座に整合的、または永続的にアトミックであると扱うべきではありません。このファイルはサンドボックス内容であり、手動編集を目的とした構成ファイルではありません。

## レジストリ アクセス モード

以下は、通常のフックされたアクセスのために選択されたモードを説明します。

| 実効モード | 高レベルの動作 |
| --- | --- |
| Normal | 通常のサンドボックス レジストリ仮想化とサポートされているマージ動作を使用します。 |
| [Open](OpenKeyPath.md) | 選択されたルールに対してホスト レジストリを直接使用します。 |
| [Open for All](OpenConfPath.md) | 同じ直接ホスト モデルを使用し、ボックス化された実行可能ファイルの対象にもなります。 |
| [Closed](ClosedKeyPath.md) | このモードが優先される場合、新しいフックされたレジストリのオープン/作成を拒否します。 |
| [Read](ReadKeyPath.md) | ホスト レジストリを直接使用しつつ、アクティブなレジストリ フィルタリングは通常ホストの変更を防ぎます。 |
| [Write / Box Only](WriteKeyPath.md) | 通常のホスト データを隠し、サンドボックス側のレジストリ状態を使用します。 |
| [Normal override](NormalKeyPath.md) | Normal ルールが優先されるときに通常の仮想化を復元します。 |

優先されるモードは、プロセス セレクターとリソース ルールの一致に依存します。[ルールの特異性](../PlusContent/RuleSpecificity.md)を参照してください。

通常の Open エントリは、通常、ボックス化された実行可能ファイルの対象制限の対象です。Open for All はその通常のゲートの外で読み込まれますが、別のルールに対して自動的に優先されたり、Windows のアクセス許可をバイパスしたりするわけではありません。

新しいフックされたオープン/作成の場合、Closed は通常のサンドボックス コピー パスの前にチェックされます。したがって、サンドボックス コピーはそのオープンを Closed から自動的に免除しません。すでに開かれているハンドルは別個です。

Read は SbieDll 内の直接ホスト パスを選択します。レジストリ フィルタリングがアクティブな標準サンドボックスでは、その読み取り専用制限は通常ドライバーに依存します。関連するフィルタリングを無効にすると、その強制の前提が変わります。ネイティブの Windows アクセス許可は依然として適用されます。

Write / Box Only は、アプリケーションがサンドボックス側のデータを読み取れないことを意味しません。より特異なアクセス可能な子孫は、ルールの一致に従って可視構造に依然として影響を与える可能性があります。

## WOW64 レジストリ ビュー

Sandboxie は、サンドボックス カウンターパートを構築する前に、選択された Windows 32/64 ビット レジストリ ビューを解決します。正規パスには `Wow6432Node` が含まれる場合があり、したがって適切な場合はサンドボックス側のパスに表示されることがあります。すべてのレジストリの場所が別個の 32 ビットと 64 ビットのストレージを持っているわけではありません。

## ハイブのライフサイクル

サンドボックス プロセスの初期化中に、Sandboxie は `RegHive` を準備またはアクセスし、`KeyRootPath` にマウントし、プロセスを共有マウントに関連付けます。複数のサンドボックス プロセスが同じハイブを共有できます。プロセスが終了するにつれて参照が解放され、ハイブが対象となったときにアンロードが調整されます。

アンロードは、最後のプロセスの終了後すぐに完了するとは限りません。ビジー状態、残っているハンドル、失敗、およびライフサイクル オプションが影響を与える可能性があります。破損したまたはアンロードできないハイブ、競合するルート/バッキングの関連付け、またはストレージの失敗は、レジストリの初期化を妨げたり、後の操作に影響を与えたりする可能性があります。マウント診断については、[SBIE1241](SBIE1241.md)を参照してください。

`RegHive` と利用可能な `RegPaths.dat` は、[スナップショット ワークフロー](../PlusContent/BoxSnapshots.md)のサンドボックス レジストリ データとして関与します。これは、アプリケーション レジストリ操作で使用される論理ホスト/サンドボックス マージとは別個です。

## 構成変更の適用

- レジストリ アクセス ルール リストはプロセスごとに初期化されます。ルール変更を確実に適用するには、影響を受けるサンドボックス プロセス ツリーを再起動してください。
- `UseRegDeleteV2` はプロセスの初期化中に選択されます。変更した後は影響を受けるプロセスを再起動してください。設定の変更は、データが入ったボックスの削除状態のインプレース変換ではありません。
- `KeyRootPath` はボックス/マウント コンテキストの一部として確立されます。変更する前に影響を受けるボックス プロセスを停止してください。パスの変更は `RegHive` またはその内容を移行しません。
- `RegPaths.dat` は、検出されたバッキング ファイルの変更後に再読み込みされる場合がありますが、即時または制限付きの同期保証はありません。

既存のレジストリ ハンドルは、すでに開かれたオブジェクトとアクセスを参照し続けます。構成変更は、それらを普遍的に再ターゲットまたは取り消しません。Windows の再起動、SandMan の再起動、またはサービスの再起動は、これらの変更の包括的な要件ではありません。

## セキュリティ境界

レジストリ仮想化は、データの表示と保存を決定します。レジストリ ルールの選択、SbieDrv フィルタリング、Windows セキュリティ記述子、およびプロセス トークン分離は別個のメカニズムです。マージされたビューはそれ自体では完全なホスト保護境界ではなく、`RegHive` は Windows アクセス チェックを置き換えません。

[アプリケーション コンパートメント](NoSecurityIsolation.md)は、セキュリティ分離を変更しながらレジストリ仮想化を保持できます。そのモードでは、[`NoSecurityFiltering`](NoSecurityFiltering.md) がドライバーのレジストリ フィルターを無効にできます。`DisableKeyFilter` もそのレイヤーに影響を与えることができます。これは、すべての SbieDll レジストリ フックを無効にするものとして読むべきではありません。

Open ルールは、ネイティブのアクセス許可が許す場合、直接ホスト レジストリ アクセスを意図的に許可します。通常モードの分離の前提を、それらの直接アクセス ルールまたは関連する強制を無効にする構成に適用してはなりません。
