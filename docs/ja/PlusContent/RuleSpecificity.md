# ルールの特異性

Sandboxie は、競合するファイル、レジストリ、および IPC リソース ルールを 2 つのモードで評価できます。古典的な評価は、アクセス モードに固定の優先順位を与えます。特異性ベースの評価は、どのアクセス モードが適用されるかを決定する前に、プロセス セレクターとリソース パターンの一致を比較します。

これらは決定の別個の部分です。

* **プロセス セレクター**は、ルールのどのプログラム固有の形式が一致するかを決定します。
* **リソース パターン**は、構成されたパスまたはオブジェクト名が要求されたリソースにどのように一致するかを決定します。
* **アクセス モード**は、勝ったルールによって表されるアクション（Closed、Read、Write、Normal、または Open など）を決定します。

ルールの特異性は、これらの部分を単純な「最長のルールが勝つ」計算に還元するものではありません。

## 特異性ベースの評価が有効になる場合

実効的な状態は次のとおりです。

```text
RestrictDevices OR UsePrivacyMode OR UseRuleSpecificity
```

`UseSecurityMode=y` はデバイス制限動作を有効にするため、ルールの特異性も有効にします。したがって、プライバシー モードまたは Restrict Devices がアクティブな間は、明示的に `UseRuleSpecificity=n` を設定しても特異性はオフになりません。

これらのオプションのいずれも機能を有効にしない通常のサンドボックスでは、古典的な評価が使用されます。構成と SandMan の動作については、[ルールの特異性の使用](../Content/UseRuleSpecificity.md)を参照してください。

## 古典的な評価

ルールの特異性が無効な場合、File および Registry ルールは固定の古典的な優先順位を使用します。

```text
Closed > Write > Read > Open > Normal > default
```

一致する Closed、Write、または Read ルールは、その優先順位レベルで比較を終了します。Normal 一致を選択できますが、一致する Open ルールがそれを置き換えることができます。このモデルでは、Open パターンがより狭いスコープに見える場合でも、Closed 一致が競合する Open 一致より優先されます。

## 特異性ベースの評価

ルールの特異性が有効な場合、Sandboxie は関連するアクセス リストから候補を比較します。プロセス セレクターが悪化せず、リソース パターンの一致がマッチャーによって考慮される特性の 1 つを改善する場合、後のアクセス リストが以前の候補を置き換えることができます。

これは、プログラム固有のルールも、より長く見えるパスも、自動的に勝者になるわけではないことを意味します。プロセス セレクターと実際のパターン一致の両方が重要です。

### プロセス セレクター

現在のプロセス マッチ レベルは次のとおりです。

| セレクター | 内部レベル |
| --- | ---: |
| 正のプロセス名、ワイルドカード名、または ProcessGroup の一致 | 0 |
| 否定セレクターの一致 | 1 |
| 明示的な `*` セレクター | 2 |
| プロセス セレクターなし | 3 |

例:

```ini
OpenFilePath=firefox.exe,C:\Path
OpenFilePath=fire*.exe,C:\Path
OpenFilePath=<Browsers>,C:\Path
OpenFilePath=!firefox.exe,C:\Path
OpenFilePath=*,C:\Path
OpenFilePath=C:\Path
```

最初の 3 つの形式はすべて、一致する場合に最高レベルを受け取ることができます。したがって、レベル 0 を正確なプロセス名一致ではなく、**一致する正のプロセス セレクター**と呼ぶ方が正確です。

より良いプロセス レベルは、クロスリスト比較中のゲートとして機能し、絶対的な優先順位ではありません。新しい候補は、より悪いプロセス レベルを持ってはならず、関連するリソース一致特性を改善する必要があります。例:

```ini
OpenFilePath=firefox.exe,C:\*
ClosedFilePath=C:\Sensitive\Records\*
```

正の Firefox セレクターだけでは、広い Open ルールがより特異な Closed 候補を置き換えることを保証しません。

### リソース パターンの一致

Sandboxie の内部的な完全一致/非完全一致の区別は、「ワイルドカードを含まない」と同じではありません。これは主に、パターンが `*` で終わるかどうかに基づいています。

```text
C:\Foo\*   non-exact
*foo*      non-exact
*.tmp      exact
foo?       can be exact
```

一致長は、パターンがテストされたリソースに正常に一致した距離を表します。ワイルドカード パターンの場合、構成されたルール内のリテラル文字数とは必ずしも一致しません。

このため、`*.tmp` は強力な候補になることがあります。完全一致として分類され、その一致は要求されたパスの末尾まで及ぶ可能性があります。すべての他のルールを普遍的に上回るわけではありません。プロセス レベル、アクセス リスト比較、他の一致プロパティ、およびタイは依然として関与します。

マッチャーはまた、直接一致と、末尾の区切り文字を付けてパスを再試行することによって生成される特定の互換性一致とを区別します。そうでなければ競合する候補が比較される場合、直接一致が優先されることがあります。

異なるアクセス リストからの候補が同じ正の一致長を持つ場合、内部ワイルドカード セグメントが少ない候補が優先されることがあります。これは、ワイルドカードが少ない方が常に勝つという普遍的なルールではありません。特に、同じリスト内のエントリ間の一般的なタイ ブレーカーではありません。

1 つのアクセス リスト内では、より長い適格な一致が以前の候補を置き換えることができます。等しい長さの候補は通常、ワイルドカードが少ないという理由だけで既存の候補を置き換えません。したがって、完全なタイでは構成順序が依然として重要になる場合がありますが、ボックス、テンプレート、フォールバック、および内部ルールの詳細な読み込み順序は、安定した公開優先順位契約として扱うべきではありません。

### アクセス リスト比較

特異性ベースの File および Registry 評価の場合、現在の走査順序は次のとおりです。

```text
Closed, Write, Read, Normal, Open
```

後のリストは、実際の一致がより良いと見なされる場合に以前の候補を置き換えることができます。比較されたすべての特性がタイの場合、以前の候補が残ります。したがって、完全なタイは次を優先します。

```text
Closed > Write > Read > Normal > Open
```

これはタイの動作にすぎません。ルールの特異性がアクティブな間、Closed が常に勝つという意味ではありません。

## ファイルおよびレジストリ ルール

File および Registry の一致は、5 つのアクセス リストを使用します。

| アクセス モード | 一般的な意味 |
| --- | --- |
| Normal | Sandboxie の通常の仮想化ポリシーを適用する |
| Open | ホスト リソースに直接アクセスする |
| Closed | アクセスを拒否する |
| Read | 実際のリソースの読み取りを許可しつつ変更を拒否する |
| Write / Box Only | サンドボックス コピーを利用可能に保ちつつホスト リソースを隠す |

これらは概念的な説明です。個々の File および Registry 操作は、Windows API レベルで必ずしも同じようにマップされるわけではありません。

たとえば、特異性が有効な場合:

```ini
UseRuleSpecificity=y
ClosedFilePath=C:\Data\*
OpenFilePath=C:\Data\App\*
```

より特異な Open ルールは、`C:\Data\App\` 以下のリソースに対して勝つことができます。特異性が無効な場合、一致する Closed ルールが古典的な評価で勝ちます。

## IPC の違い

一般的な名前付き IPC オブジェクトの一致は、同じ 5 リスト比較を使用しません。次を使用します。

```text
NormalIpcPath
OpenIpcPath
ClosedIpcPath
```

特異性がアクティブな場合、より特異な Normal または Open の IPC 候補が、同じ比較原則の下でより広い Closed 候補を置き換えることができます。[通常の IPC パス](../Content/NormalIpcPath.md)を参照してください。

`ReadIpcPath` は異なります。その文書化された `$:` 形式は、主に別個のプロセス/スレッド アクセス ポリシーに属します。

```ini
ClosedIpcPath=$:target.exe
OpenIpcPath=$:target.exe
ReadIpcPath=$:target.exe
```

これらのターゲット プロセス ルールは、独自のマッチャーと Closed、Open、次に Read という関連する順序を使用します。上記のリソース パス特異性レベルは使用しません。[IPC パスの読み取り](../Content/ReadIpcPath.md)を参照してください。

## 構成パターンの詳細

構成された File および Registry ルールは通常、パターンに `*` が含まれていない場合、暗黙のサフィックス スター処理を受けます。たとえば、次のような構成されたルール:

```ini
NormalFilePath=C:\Foo
```

は `C:\Foo*` と等価として読み込まれる場合があります。これはルールのスコープとその完全一致/非完全一致の分類を変更します。先頭の `|` はその自動サフィックスを抑制し、File/Registry の一致の前に削除されます。

IPC パス リストは同じ暗黙の末尾 `*` を受け取りません。より広い一致を意図する場合は、IPC ワイルドカードを明示的に記述してください。
