# 实战追踪指南

本页是 [跟踪日志](TraceLog.md) 的实操补充。该页讲的是追踪机制本身（缓冲区、栈追踪、性能影响），本页按当前驱动的真实行为，讲怎么拿到一份有用的日志并读懂它，同时梳理清楚哪些追踪设置当前有效、哪些只是历史遗留的元数据。

本页内容适用于当前版本（1.18.x）。如果你从旧文档或旧论坛帖子过来，请注意下文的“当前设置与遗留名称”对照表——若干被广泛引用的追踪选项名早已不再产生任何作用。

## 三个前提条件

资源追踪只记录你要求它记录的内容。以下三项必须齐备，其中第一项是大多数人卡住的地方：

1. **开启监控**。在 SandMan 中选择**「视图(V)」→「跟踪日志记录」**（使用独立跟踪监视器时位于「选项 → 全局设置 → 高级选项」）。注意这个开关在**视图菜单**里——不是跟踪日志面板内部的按钮，单独点开面板并不会启用它。

2. **配置沙盒级追踪掩码**。沙盒只记录其追踪设置所要求的访问类型（驱动在进程启动时读取这些设置）。首次诊断文件和注册表访问建议这样配置：

    ```ini
    [MyBox]
    FileTrace=ad
    KeyTrace=ad
    IpcTrace=ad
    ```

    缺少这些行时，无论全局开关如何设置，跟踪日志都会完全空白。同一批设置也可在 SandMan 的「沙盒选项 → 高级选项 → 追踪」中勾选。

3. **在追踪开启期间复现问题**。只有监控处于活动状态期间发生的访问才会被记录；日志是实时数据流，不是历史档案。

## 当前追踪设置与遗留名称

当前驱动实际读取的追踪选项如下：

| 设置 | 记录内容 |
| --- | --- |
| `FileTrace` | 文件访问 |
| `KeyTrace` | 注册表访问 |
| `IpcTrace` | IPC 对象访问（命名对象、节区、RPC） |
| `PipeTrace` | 命名管道访问 |
| `CallTrace` | 系统调用层记录 |
| `GuiTrace` | GUI 相关记录 |

每个设置的值是若干字符的组合：

| 字符 | 记录内容 |
| --- | --- |
| `a` | 被放行的访问 |
| `d` | 被拒绝的访问 |
| `i` | 需要忽略的访问 |
| `*` | 以上全部 |

因此 `FileTrace=ad` 会同时记录成功和被拦截的文件访问——这通常是正确的起点。

!!! warning

    旧文档和 wiki 页面还会提到 `ApiTrace`、`HookTrace`、`ErrorTrace` 和 `DebugTrace`。这些名称在设置元数据文件里依然存在，但当前驱动中没有任何代码路径读取它们：设置它们**毫无作用**。如果某份指南告诉你启用 `ApiTrace` 以查看程序行为，它描述的是更老版本的 Sandboxie。

## 确认追踪是否真的在工作

分析日志之前，先端到端确认整条链路通畅：

1. 打开**「视图(V)」→「跟踪日志记录」**。
2. 在已配置追踪的沙盒里启动一个短命程序——例如在沙盒中启动 `notepad`。
3. 观察跟踪日志面板。如果出现记录，说明监控已激活、掩码已生效。
4. 如果面板始终空白，常见原因有：全局开关未开（见上面第 1 项）、沙盒没有追踪掩码、或者你期待的访问发生在**开启追踪之前**。

这个快速自检能把“监控没运行”和“没发生什么值得记录的访问”区分开——这两者很容易混淆。

## 两种导出格式

跟踪视图有两种显示模式，导出的内容也不同：

- **Monitor 模式**（默认的树形视图）按资源显示聚合计数。从该模式导出的是聚合表——适合快速浏览，但没有逐条明细。
- **Trace 日志模式**（关掉工具栏的 monitor-mode 切换开关）显示单条记录。从该模式导出的是制表符分隔的文件，每行一条记录：时间戳、进程、PID、TID、类型、状态、名称和消息。分析和在 issue 里分享请用这个格式。

请先切换到 Trace 日志模式，再点跟踪视图工具栏的**「保存到文件」**按钮（软盘图标）。

## 一个让多数人意外的行为

**命中 Closed 规则被拒绝的访问不会被记录。** 只有当访问路径没有命中任何显式路径规则时，监控才会写入拒绝记录——`ClosedFilePath` 正常命中属于规则按设计生效，不留痕迹。

实际影响是：任何从跟踪日志里收集“被拒绝记录”并据此建议放行规则的工具，收到的恰好是错误的那些；而隐私/安全类沙盒（`ClosedFilePath`、`ClosedKeyPath` 以及隐私模式的整套锁定清单）根本不会产生任何拒绝记录。

## 诊断在更严格沙盒中失败的程序

正确的方向与追踪表面上的暗示恰好相反：

1. 让程序在**能够正常工作**的沙盒里完整运行一遍，并在该沙盒上设置 `FileTrace=ad`（按需添加其他掩码）；
2. 导出跟踪日志（Trace 日志模式）；
3. 把记录到的访问与程序**失败**的那个沙盒的拦截规则（`ClosedFilePath`、`ClosedKeyPath`、`ClosedIpcPath`、`BlockNetworkFiles`）进行比对——命中目标沙盒拦截规则的访问即为候选项；
4. 只为这些资源补充放行规则，在目标沙盒中重新测试。

第 3 步是机械操作——小脚本可以代劳——但判断权始终在你手里：决定开放哪些资源，并优先使用能满足需求的最小规则（程序只读时用只读规则）。

## 性能提示

追踪不是免费的：每条记录都有开销，栈追踪开销更大。详见[性能影响](TraceLog.md#performance-impact)。请让掩码保持与排查需求相称的最小范围——所有类别全开 `*` 很少是正确的起点。
