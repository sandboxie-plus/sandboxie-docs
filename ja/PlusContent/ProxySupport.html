    プロキシ サポート

    概要

    一致するプロセスについて、Sandboxie はサポートされている Winsock TCP 接続パスを選択された SOCKS5 プロキシ経由にリダイレクトします。標準の傍受されるパスには connect、WSAConnect、および ConnectEx が含まれますが、この一覧を網羅的な API 契約として扱うべきではありません。

    この機能は、IPv4 および IPv6 の TCP 宛先に対する SOCKS5 CONNECT コマンドを実装しています。認証なしの SOCKS5 接続、およびユーザー名/パスワード認証をサポートします。

    SOCKS4、SOCKS4a、HTTP CONNECT、汎用 HTTP または HTTPS プロキシ、SOCKS5 BIND、SOCKS5 UDP ASSOCIATE、または UDP プロキシは提供しません。UDP の送受信パスは SOCKS5 経由でルーティングされません。この機能は VPN ではなく、傍受された Winsock パスを迂回するネットワーキング メカニズムを透過的にカバーするものではありません。

    SandMan の構成

    Sandboxie Plus で、Sandbox Options > Network Options > Internet Proxy を開きます。単一のマスター チェックボックスはありません。プロキシ ルールは、追加、削除、有効化/無効化、および並べ替えができます。

    ルール リストには、プログラム、プロキシ アドレス、ポート、認証モード、ログイン、パスワード、およびバイパス アドレスのフィールドが含まれます。プロキシ アドレス列は現在 IP と表示されていますが、ホスト名も受け付けます。

    NetworkUseProxy の構文

    一般的な構文は次のとおりです。

    NetworkUseProxy=[process,]Address=<proxy-address>;Port=<port>[;Auth=Yes|No][;Login=<user>][;Password=<password>|;EncryptedPW=<value>][;Bypass=<address-or-range>,...]

    たとえば、このルールはサンドボックス内のすべてのプロセスに適用されます。

    NetworkUseProxy=*,Address=192.0.2.10;Port=1080;Auth=No

    このルールは browser.exe にのみ適用され、ユーザー名/パスワード認証を使用します。

    NetworkUseProxy=browser.exe,Address=proxy.example;Port=1080;Auth=Yes;Login=user;EncryptedPW=<value>

    SandMan は通常、保存されたパスワード値を含め、これらのエントリを作成およびシリアル化します。ユーザーは通常、EncryptedPW を手動で構築する必要はありません。

    プロキシ アドレスは、IPv4 アドレス、IPv6 アドレス、またはホスト名にできます。ホスト名が SOCKS サーバーを識別する場合、Sandboxie はプロキシ構成を初期化する際にそれをローカルで解決します。プロキシ サーバーにホスト名を使用しても、その DNS ルックアップは隠されません。

    アプリケーションのマッチング

    ルールは * を使用してサンドボックス内のすべてのプロセスに適用することも、特定の実行可能ファイルに適用することもできます。完全一致の実行可能ファイルのマッチは、グローバル ルールより優先されます。同じアドレス ファミリと特異性では、最初の適用可能な有効なルールが使用されます。

    繰り返しルールは、フェイルオーバー、ラウンドロビン選択、またはロード バランシングを提供しません。同じサンドボックス内の異なるアプリケーションに異なるプロキシが必要な場合は、実行可能ファイル固有の別個のルールを使用してください。

    IPv4 と IPv6

    プロキシの選択はアドレス ファミリを認識します。

    • IPv4 宛先には、適用可能な IPv4 プロキシ エンドポイントが必要です。
    • IPv6 宛先には、適用可能な IPv6 プロキシ エンドポイントが必要です。

    IPv4 プロキシ エンドポイントは IPv6 宛先に自動的に使用されず、その逆も同様です。有効なプロキシ構成が存在しても、宛先のアドレス ファミリで利用可能なプロキシ エンドポイントがない場合、Sandboxie は元の宛先に直接接続するのではなく、接続を失敗させます。

    IPv4 と IPv6 の両方のアドレスに解決されるプロキシ ホスト名は、各ファミリのエンドポイントを提供できます。

    認証と資格情報

    各プロキシ ルールは、認証なしの SOCKS5 または SOCKS5 ユーザー名/パスワード認証を使用できます。SandMan はログインとパスワードを受け入れ、それらをサンドボックス構成へのシリアル化を処理します。

    Sandboxie 構成に保存されたプロキシ資格情報は、構成シークレットとして扱い、それに応じて保護する必要があります。構成は安全な資格情報ボールトではなく、エンコード/暗号化されたパスワード表現またはプレーンテキストのフォールバックのいずれかを含む場合があります。手動で記述されたエントリでは、任意の区切り文字や引用符文字が安全にエスケープされると仮定せず、任意の資格情報文字が UTF-8 としてエンコードされると依存しないでください。

    バイパス アドレス

    省略可能な Bypass フィールドは、コンマで区切られた宛先 IP アドレスと IP 範囲を受け入れます。

    NetworkUseProxy=*,Address=192.0.2.10;Port=1080;Auth=No;Bypass=127.0.0.1,192.168.0.0-192.168.255.255

    バイパス エントリに一致する宛先は、SOCKS プロキシを使用せずに接続されます。localhost の宛先もプロキシ経由でリダイレクトされません。この意図的な直接ルーティング動作は、プロキシのみの接続が期待される場合に重要です。

    バイパス処理は、独立した Sandboxie のネットワーク ブロック ルールを上書きしません。別途ブロックされた宛先は、そのポリシーの対象のままです。

    失敗時の動作

    Sandboxie が有効なプロキシ ルールを選択した後、プロキシへの接続失敗、認証または SOCKS ネゴシエーションの失敗、宛先の拒否、または必要なアドレス ファミリのプロキシ エンドポイントの不在は、元の宛先への直接の再試行を引き起こしません。アプリケーションは接続失敗を受け取ります。正確な Winsock エラーは失敗パスによって異なる場合があります。

    ただし、完全に無効なプロキシ構成は、プロキシが有効にならない結果となり、接続が通常どおり続行される可能性があります。したがって、プロキシ構成だけを無条件のフェイルクローズ プライバシー メカニズムとして扱うべきではありません。直接接続を防ぐ必要がある場合は、プロキシ ルールに加えて別個のネットワーク層の制限を適用してください。

    セキュリティとプライバシーの制限

    SOCKS プロキシは SbieDll のユーザー モード傍受を通じて実装されています。サポートされている傍受された Winsock パスを使用する一致するアプリケーションの直接 TCP 接続を削減しますが、ファイアウォールではなく、Windows Filtering Platform (WFP) ルールを自動的に作成するものでもありません。

    他の低レベル ネットワーキング メカニズムを使用するコードを含め、これらのパスを迂回するアプリケーションまたはコンポーネントは、リダイレクトされない場合があります。また、プロキシは、アプリケーションまたはプロキシ関連の DNS ルックアップがリモートで発生する保証として扱うべきではありません。

    直接トラフィックをより強力に制御するには、プロキシ構成を適切な WFP およびネットワーク アクセス ルールと組み合わせてください。ネットワーク層フィルターは、SOCKS セッション内で運ばれる最終的な宛先ではなく、プロキシ エンドポイントへの実際の接続を監視します。

    詳細および実験的な設定

    NetworkProxyResolveHostnames

    NetworkProxyResolveHostnames は現在の設定メタデータに存在しますが、標準ビルドは現在その実装を有効にしておらず、SandMan はコントロールを公開していません。リモート DNS 解決や DNS リークの防止のために依存すべきではありません。

    UseProxyThreads

    UseProxyThreads=y は既定で無効になっている実験的な互換モードです。サンドボックス化されたプロセス内でプロキシされた接続ごとにローカル TCP リレーを作成します。アプリケーションはローカル リレーに接続し、ワーカー スレッドが SOCKS プロキシに接続してデータをリレーします。

    この設定は、パフォーマンス、プライバシー、またはより強力なネットワーク強制ではなく、まれな互換性ケースを対象としています。現在のランタイムは Developer または Eternal 証明書に対してのみそれを読み取り、SandMan は同じ条件の下でのみそのチェックボックスを公開します。手動で設定しても、通常の証明書に対してモードが有効になることはありません。

    リレーは別個のワーカー接続を使用し、通常のプロキシ パスと同じ送信元アドレス バインディング保証を提供すると扱うべきではありません。

    バインディングおよびネットワーク ポリシーとの相互作用

    送信元アドレスまたはアダプターのバインディングは、通常の SOCKS プロキシ接続の前に評価されます。したがって、利用できない厳密なバインディングは、プロキシへの接続を妨げる可能性があります。詳細なバインディング動作は、アダプターのバインドとアダプター IP のバインドで文書化されています。

    WFP 強制なしでは、Sandboxie のユーザー モード宛先ポリシーはプロキシ リダイレクトの前に元の宛先を評価します。WFP 強制ありでは、ネットワーク スタックは SOCKS セッションにカプセル化された宛先ではなく、プロキシ エンドポイントへの実際の接続を監視します。プロキシを有効にしても、直接接続をブロックする WFP ルールが自動的に追加されることはありません。

    構成変更の適用

    NetworkUseProxy ルールは、サンドボックス化されたプロセスが Winsock を初期化するときに初期化されます。プロキシ ルールを変更した後は、新しい構成が使用されるように、影響を受けるサンドボックス化されたプロセスを再起動してください。UseProxyThreads の変更も、影響を受けるプロセスの再起動が必要です。SandMan または Sandboxie サービスの再起動は通常必要ありません。

    Sandboxie Plus と Classic

    プロキシ ランタイムは共有 SbieDll コードに実装されています。SandMan は現在のプロキシ構成インターフェイスを提供します。Sandboxie Control Classic は、機能が利用可能な場合、共有ランタイムを通じて互換性のある手動構成設定を消費できますが、同等の最新のプロキシ インターフェイスを提供しません。

    プロジェクトの現在の機能可用性の概要については、機能比較を参照してください。
